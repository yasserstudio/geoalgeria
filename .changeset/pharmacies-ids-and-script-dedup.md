"@geoalgeria/pharmacies": minor

**Migration.** Twenty-nine ids are retired, and `data/retired-ids.json` now forwards every one of them to the id that carries that pharmacy today, so an old join key is followed rather than only found missing. Each forward is a single hop; none leads to another retired id.

Seventeen records carried a wilaya prefix their own `wilaya_code` contradicted, and are re-issued into the id space of the wilaya they are actually in: `02-00160` → `48-00142`, `07-00018` → `51-00040`, `13-00009` → `22-00080`, `13-00010` → `22-00081`, `16-00279` → `35-00091`, `21-00036` → `23-00061`, `21-00037` → `23-00062`, `21-00038` → `23-00063`, `22-00039` → `13-00089`, `22-00078` → `13-00090`, `22-00079` → `13-00088`, `25-00049` → `43-00111`, `40-00003` → `05-00072`, `61-00005` → `07-00055`, `65-00020` → `68-00023`, `65-00025` → `68-00024`, `68-00001` → `28-00049`.

Twelve pharmacies were published twice and are now one record each, the retired id forwarding to the kept one: `02-00063` → `02-00062`, `07-00052` → `07-00002`, `10-00021` → `10-00019`, `14-00032` → `14-00031`, `16-00426` → `16-00178`, `19-00074` → `19-00073`, `23-00042` → `23-00044`, `39-00004` → `39-00003`, `43-00052` → `43-00051`, `43-00079` → `43-00004`, `51-00039` → `51-00036`, `55-00017` → `55-00018`. The record count falls from 3,807 to 3,795 and nothing was deleted.

**The id's wilaya prefix is now always the record's own wilaya.** `types/index.d.ts` documents the id as `{wilaya_code}-{seq}`, which invites a consumer to read the wilaya off the prefix, and on 17 of 3,807 records that read gave the wrong wilaya. The cause was id stability working against the contract: a record is pinned back to the id it shipped under, keyed on its OpenStreetMap element, so that a new pharmacy does not re-sequence every later id in its wilaya. When the commune join later moved a record to another wilaya, the pin brought back the whole old id, prefix included, and the prefix stayed wrong for good. Several of the 17 are neighbours across a wilaya border and several are in the 2026-reform wilayas, which is where the join moved most. The generator now treats a prefix that no longer describes the record as a reason not to pin: the stale id retires, the record takes the id its own wilaya gives it, and the forward keeps the old key resolvable. A test fails the build if any id prefix and `wilaya_code` ever disagree again. Every one of the 17 new wilayas is the commune whose OpenStreetMap outline contains the point, not a claim read back off the id.

**Names that hold two languages at once are split, so `name_ar` is Arabic and nothing else.** OpenStreetMap contributors routinely write both languages into one tag, `name=Pharmacie bouchekouf صيدلية بوشقوف`, and the old router asked only whether a value contained an Arabic letter, so 28 records shipped a `name_ar` that was mostly Latin. Such a value is now cut at the script boundary and each field keeps its own half; six records gain the `name_fr` that was sitting inside their Arabic tag. The cut only ever removes the separator between the halves: nothing is transliterated, translated or tidied, and a name written in one script is passed through exactly as tagged, so `24 ساعة` keeps its number. 848 records carry an Arabic name and 2,416 a Latin one, 809 both.

**De-duplication compares Loose keys per script instead of exact text.** The same string comparison that mis-routed the names also decided which records were one pharmacy, as lowercase text within 40 m, so `43-00004` "Pharmacie bouchekouf صيدلية بوشقوف" and `43-00079` "بوشقوف", 6.6 m apart in Oued Endja, never matched. Names are now folded through [`@geoalgeria/normalize`](https://github.com/yasserstudio/geoalgeria/tree/main/packages/normalize) Loose keys, one key per script after the split, with the words that only say "pharmacy" dropped, which is what lets the Arabic half of one spelling meet the whole of the other. That found 12 pairs dataset-wide, every one inside a single wilaya. Oued Endja is corroborated by the Mila wilaya pharmacy duty roster for October 2026, an official source outside OpenStreetMap, which lists exactly one بوشقوف among the commune's pharmacists. The survivor of a pair is the record already published, then the one carrying the most fields, then the lower OpenStreetMap id, so a collapse never retires an id it could have kept and never depends on the order Overpass answered in. A test fails the build if two records within 40 m ever share a name key again, or if `name_ar` holds a Latin letter.

**A collapse costs no contact detail.** The kept record of a pair absorbs every field it lacks from the record it replaces, so phone, opening hours, address, operator and the `dispensing` flag all survive de-duplication. Three dispensing flags that only the retired side carried are now on the kept record: `07-00002`, `16-00178` and `51-00036`. Where both records state a field, the kept record's own value stands; nothing is merged or concatenated. Two such disagreements exist, both on `51-00036` over `51-00039`: opening hours `24/7` against `08:00-22:00`, and the address, which the kept record gives in Arabic with a postcode and the other in Latin without one. Every other field a retired record held was already on the kept one, either identically (`14-00031` phone, hours and address; `02-00062` and `55-00018` address) or as a spelling variant of a name.

Counts move with the smaller, cleaner set: 2,455 named rather than 2,467, 145 with a phone rather than 146, 256 with opening hours rather than 257, 1,161 with an address rather than 1,164, 3,499 `exact` and 296 `approximate`, still across 67 wilayas. Those three drops are duplicate values de-duplicated, not information lost: in every case the pharmacy's one remaining record states the same phone, hours or address that both of its records used to state. `dispensing` rises to 530 from 529, because the carry-over also recovers a flag, an opening-hours string and an address from three records that an earlier release's de-duplication had already dropped silently.
