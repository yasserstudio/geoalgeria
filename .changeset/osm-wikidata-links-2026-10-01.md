Every commune and wilaya now links to its own OpenStreetMap relation and to Wikidata.

**Two new fields.** `osm_relation_id` is the id of the OpenStreetMap administrative relation that is this record upstream, `admin_level=8` for a commune and `admin_level=4` for a wilaya; `wikidata` is the Q item that relation is tagged with. They exist so a consumer can fetch a boundary, a population or an article for a GeoAlgeria record instead of matching it by name, which is the join this dataset tells everyone else not to make.

```js
const dz = require("geoalgeria");
const [commune] = dz.findCommune("Tamanrasset");
// → { …, code_commune: 1101, osm_relation_id: 4175374, wikidata: "Q205792" }
// https://www.openstreetmap.org/relation/4175374  https://www.wikidata.org/wiki/Q205792
```

**Coverage.** 1,537 of the 1,541 communes carry a relation and 1,536 carry a Wikidata item; all 69 wilayas carry both. Four communes carry neither, because the capture holds no relation for them: Souk Oufella (630), Bir Touta (1634), Collo (2110) and Dhayet Bendhahoua (4703). One commune carries a relation with no item, Ain-Defla (4401), whose relation has no `wikidata` tag. Null means the source has none; nothing is filled in by inference.

**Nothing is matched by name.** The ids are harvested from the Overpass capture the commune-centre audit of 2026-09-29 already fetched, `timestamp_osm_base` **2026-09-29T12:54:47Z**, through the linkage that audit wrote to `research/_commune-centres/osm-seat-reference.json`: 1,477 communes joined on the relation's `ref:ONS` tag, 54 on a pre-2019-reform ONS code resolved inside the mother wilaya's carved-out communes, and 6 on reviewed per-relation pins where OpenStreetMap and this dataset spell the same ONS code differently. Wilayas join on the relation's `ref`. A wilaya links to its own province relation, never to its capital commune's, even though the two share a point.

**Carriers.** The JSON records: `data/algeria.json` at both of its levels, `data/communes_w*.json` and `data/wilayas.json`. The CSV, GeoJSON, SQL and e-commerce mirrors do not carry the two ids in this release; `data/README.md` says so per file. TypeScript gains them on `Commune`, `Wilaya` and `WilayaDetailed`.

**Provenance** is a new file, `data/osm-links.metadata.json`: the capture, the Overpass `timestamp_osm_base`, the join rule, the coverage counts and the five records with a null, regenerated by `node scripts/add-osm-links.mjs --write` and held by `--check`.

The dataset validator now requires both fields on every commune and wilaya, checks their shape (a positive integer relation id, `Q` followed by digits) and fails if one relation id or one Wikidata item appears on two records: one relation is one place, so a repeat is an upstream or linkage defect to report rather than a join that answers twice. `test/osm-wikidata-links.test.mjs` adds the same checks, asserts every published value is the one the audit's linkage carries, that the audit decided each linkage on an ONS code or a reviewed pin and never on a name alone, and that `data/algeria.json` has not drifted from the flagship records.

**Licence.** Both values are read out of OpenStreetMap, so they are ODbL 1.0, © OpenStreetMap contributors, a fourth carve-out in the package `LICENSE` and `NOTICE` alongside the boundary polygons, the OSM-derived commune centres and the wilaya capital points. The Wikidata items are OpenStreetMap tag values, not the result of a query against Wikidata.

Refs yasserstudio/geoalgeria.com#181.
