Read the DGPC's own commune name through a one-character spelling difference, and otherwise join a unit's commune by the commune outline that contains it rather than by the nearest commune centre: 18 of the 880 units move to the commune they are actually in.

The DGPC publishes a commune name per unit (`commune_1`). The old join matched it by exact equality on a folded Arabic key and sent everything else to the nearest commune centre inside the derived wilaya. Both halves were wrong. A centre is not a boundary, so a centre that sits closer than the commune whose outline holds the point won whenever two communes are unevenly shaped. And exact equality meant one missing alef demoted a unit to geometry, which then overruled the source that had named the commune correctly all along.

The join now has five clauses, in `scripts/lib/protection-civile-commune.mjs` so they can be tested on fixtures rather than on the country: the DGPC's name exactly (782 units); that name across up to two edits when exactly one commune of the wilaya is that close (84 applied, 1 refused); the commune whose OpenStreetMap outline contains the point (13); and the nearest centre, which no longer runs for any unit. Containment comes from the repository's shared resolver and is searched **globally**, with the derived wilaya filtering the answer rather than scoping the search, so an outline overlap that crosses a wilaya line cannot discard a good in-wilaya outline. A coordinate too rounded to be a point at all skips containment entirely, the same `MIN_EXACT_DECIMALS` rule the shared resolver applies.

**18 units re-placed**, each into the commune whose outline contains it: `06-019` Smaoun to Fenaia Il Maten, `10-005` Djebahia to Aomar, `10-014` El Khabouzia to Bir Ghbalou, `10-026` Ath Mansour to Hanif, `14-002` Mechraa Sfa to Rahouia, `15-006` Ait Aggouacha to Larbaa Nath Irathen, `19-010` Beni Chebana to Beni Ourtilane, `31-010` Ben Freha to Boufatis, `32-009` Sidi Slimane to Kef El Ahmar, `34-003` El Annasseur to Bordj Bou Arreridj, `39-006` Oued El Alenda to Mih Ouansa, `42-003` Bou Haroun to Ain Tagourait, `49-003` Ksar Kaddour to Tinerkouk, `53-001` Foggaret Ezzoua to Ain Salah, `53-003` Ain Salah to Inghar, `55-005` and `55-006` Nezla to Touggourt, `68-001` Menaâ to Medjedel. Ids, coordinates, names, wilaya codes, precision and contact fields are untouched, and `wilaya_code` still comes from the boundary-plus-DGPC reconciliation: the containing outline only picks within the wilaya that reconciliation decided.

**Three units the outline alone would have moved and this join does not.** `23-017` at (36.8269, 7.60981) is inside El Bouni's outline (2305) while Sidi Amar's centre is nearer, so the old centroid join moved it to a commune that does not contain it. The DGPC in turn files it under "وادي العنب", one edit from Oued El Aneb (2306), with its unit name and address agreeing, but the point is 65 m outside Oued El Aneb's reduced outline and 86 m inside El Bouni's. A match inside the edit window is an inference about what the source meant, not the source speaking plainly, and an inference must not dislodge a published commune whose own outline confirms it, so the unit stays in El Bouni. `16-048` (the Ben Aknoun zoo unit, "بن عكنون" against the registry's "ابن عكنون") and `33-007` ("إن أميناس" against "إن أمناس") are the opposite case: there the DGPC's name agrees with what is published and only the outline disagrees, so the source decides and they keep Ben Aknoun (1622) and In Amenas (3306).
